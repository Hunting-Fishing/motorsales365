## Fail-fast execution and integration policy

1. Define one bounded deliverable, exact success check and owner before starting.
   Reuse the integrated candidate and existing components; new isolated models
   are justified only by a named integration/release dependency.
2. On an action failure, diagnose it once. Try **at most one safe alternative**
   when one exists within current authorization. Do not repeat the same failed
   action, switch tools to bypass access controls, relax tests or force a write.
3. If that alternative also fails, or no safe alternative exists, **stop the
   affected action and notify the owner** with failure evidence, the alternative
   attempted (or why unsafe), exact blocker, needed help and schedule impact.
   Continue independent in-scope lanes. Record the stop across scheduled turns;
   resume only on new access, source, configuration or owner direction.
4. Unknown financial/stock/Storage outcomes are not safe retry candidates.
   Reconcile the durable operation outcome first; do not create duplicate writes.
5. Parallelize bounded, non-overlapping implementation/review where capacity
   exists. One integrator owns shared files/commits; no concurrent shared-checkout
   branch switches. Serialize memory-heavy suites/build/typecheck. Run focused
   tests while editing and required complete gates on integrated candidates;
   do not endlessly repeat unchanged Windows scanner/full-suite failures.
6. Preserve user changes, historical evidence, required PG17/adversarial-role/
   transaction coverage and normal timeouts/quarantine. No Docker, paid resources,
   customer outreach, destructive repair or unreviewed production experiments.
